# NullOps: Full Working App with Docker Compose

A small production-like stack run with Docker Compose: a Flask web app backed by
MariaDB, served through an Nginx reverse proxy, monitored with cAdvisor, and with
**every credential stored in HashiCorp Vault** instead of `.env`.

## Architecture

```
            host :80                      host :8081                 host :8200
               |                              |                           |
          +---------+                   +-----------+              +-------------+
          |  nginx  |                   |  cadvisor |              |    vault    |
          +---------+                   +-----------+              |  UI / API   |
               |  frontend network                                 +-------------+
          +---------+                                                     ^
          |   app   |  Flask + gunicorn, non-root user                    |
          +---------+ ------------------ AppRole login, reads db creds ----+
               |  backend network                                         |
          +---------+                                                     |
          |   db    |  MariaDB 11.4, data in named volume "dbdata"        |
          +---------+ <--- credential files rendered by vault-bootstrap ---+
```

| Service           | Image                              | Purpose                                        |
|-------------------|------------------------------------|------------------------------------------------|
| `vault`           | `hashicorp/vault:1.17`             | Secret store: holds every database credential   |
| `vault-bootstrap` | `hashicorp/vault:1.17`             | One-shot job: init/unseal, seed secrets, AppRole |
| `db`              | `mariadb:11.4`                     | Stores visits; data persists in `dbdata`        |
| `app`             | built from `./app`                 | Flask API (`/`, `/health`)                      |
| `nginx`           | `nginx:1.27-alpine`                | Reverse proxy, the only public web entry        |
| `cadvisor`        | `gcr.io/cadvisor/cadvisor:v0.49.1` | CPU / memory / network per container            |

Design choices:

- **No credentials outside Vault.** `.env` holds ports and names only. The database
  passwords are generated by `vault-bootstrap` on first start, stored in Vault and never
  written to `.env`, `docker-compose.yml` or any image.
- **Vault is its own distributed service.** It runs in a separate container with its own
  storage volume, is reached over the network (`http://vault:8200`), and is the single
  source of truth other services depend on.
- **Least privilege.** The app authenticates with an AppRole whose policy allows reading
  exactly one path (`nullops/data/db/app`). It cannot read the MariaDB root password or
  write anything.
- **Healthchecks on every service.** Startup order uses `depends_on`, so `db` waits until
  Vault is bootstrapped, `app` waits until Vault is unsealed *and* MariaDB accepts
  connections, and `nginx` waits until the app is healthy.
- **Two networks.** `db` and `vault` are only on `backend`, so neither Nginx nor cAdvisor
  can reach them.
- **Non-root app container** (`appuser`, uid 10001); dependencies are declared in
  `app/pyproject.toml` and pinned in `app/uv.lock`, installed with
  [uv](https://github.com/astral-sh/uv) (`uv sync --locked`) instead of pip, so every
  build is fast and reproducible.
- **Safe startup with replicas.** Schema creation takes a MariaDB named lock (`GET_LOCK`),
  so several app replicas starting at once create the table one at a time.
- **`restart: unless-stopped`** so services come back after a crash or a Docker restart.

## Quick start

```bash
cp .env.example .env        # no password to edit: there are none
docker compose up --build -d
docker compose ps           # every service should show (healthy)
```

| URL                          | What you see                                            |
|------------------------------|---------------------------------------------------------|
| http://localhost/            | JSON with a visit counter stored in MariaDB             |
| http://localhost/health      | `{"status":"ok","database":"reachable","secrets":"vault"}` |
| http://localhost:8081/       | cAdvisor dashboard                                      |
| http://localhost:8200/ui/    | Vault UI (log in with the root token, see below)        |

Ports can be changed with `NGINX_PORT`, `CADVISOR_PORT` and `VAULT_PORT` in `.env`, and
the number of gunicorn workers per app container with `APP_WORKERS` (default 2).

Stop the stack (data and secrets are kept):

```bash
docker compose down
```

Stop and delete the volumes too — this wipes the database **and** Vault, so the next
start generates brand new passwords:

```bash
docker compose down -v
```

## Secrets with Vault

### How a credential reaches each service

```
vault-bootstrap (root token, runs once per "up")
   |
   |-- vault operator init / unseal        -> unseal key + root token in volume "vault-init"
   |-- generates 2 random 32-char passwords
   |-- vault kv put nullops/db/app         -> username, password, database
   |-- vault kv put nullops/db/root        -> MariaDB root password
   |-- AppRole "nullops-app" + policy      -> role_id / secret_id in volume "vault-approle"
   |-- renders credential files            -> volume "db-secrets"
   |
   +--> app: reads role_id/secret_id, logs into Vault, reads nullops/db/app over HTTP
   +--> db : reads MARIADB_*_FILE from db-secrets (MariaDB cannot talk to Vault itself)
```

- `nullops/` is a KV v2 mount, so every write keeps a version history.
- The app never holds a Vault token in its environment: it exchanges the AppRole
  `role_id` + `secret_id` for a short-lived token (`token_ttl=1h`) at startup.
- Handing the `secret_id` to the workload through a volume is the *trusted orchestrator*
  pattern — Compose is trusted to deliver it, exactly like Vault Agent does on Kubernetes.
- MariaDB only reads its credential files on first initialisation; after that the
  password lives in `dbdata` and in Vault.

### Reading secrets by hand

The root token and unseal key are the output of `vault operator init`, kept in the
`vault-init` volume:

```bash
docker compose run --rm --entrypoint "" vault-bootstrap cat /vault/init/init.txt
```

With that token you can use the UI at http://localhost:8200/ui/ or the CLI:

```bash
ROOT_TOKEN=$(docker compose run --rm --entrypoint "" -T vault-bootstrap \
  awk '/^Initial Root Token:/ {print $4}' /vault/init/init.txt)

docker compose exec -e VAULT_TOKEN="$ROOT_TOKEN" vault vault kv get nullops/db/app
docker compose exec -e VAULT_TOKEN="$ROOT_TOKEN" vault vault policy read nullops-app
```

### What a real deployment would do differently

This stack is a lab, so three shortcuts are deliberate and marked here:

| Shortcut                                   | Production equivalent                                  |
|--------------------------------------------|--------------------------------------------------------|
| 1 unseal key share, stored in a volume     | 5 shares / 3 threshold held by operators, or auto-unseal with a cloud KMS / Transit |
| `tls_disable = true` on the listener       | TLS certificate on the Vault listener                  |
| Static KV password for MariaDB             | Vault's database secrets engine issuing short-lived, per-service credentials |

## Labs

### Lab 1: Reverse proxy
`nginx/nginx.conf` forwards every request to the `app` upstream and sets the
`X-Real-IP` / `X-Forwarded-*` headers. Check it:

```bash
curl -i http://localhost/          # Server: nginx, body comes from Flask
docker compose logs app | tail     # the request appears in gunicorn's access log
```

### Request logging and correlation

The Flask app writes JSON logs to stdout, including a `request_completed` event
with the method, path, status, duration, and request key. Send `X-Request-Key`
to correlate a request with its logs; the response returns the same key. Keys
must be 1–128 characters using ASCII letters, digits, `.`, `_`, or `-`. Missing
or invalid keys are replaced with a generated UUID-based key. Query strings are
not included in request completion logs. Gunicorn and Nginx keep their own logs.

```bash
curl -i -H 'X-Request-Key: example-123' http://localhost/health
docker compose logs app
```

Run the request logging tests with `cd app && uv run pytest`.

### Lab 2: Healthchecks

```bash
docker compose ps                  # STATUS column shows (healthy)
docker inspect --format '{{json .State.Health}}' nullops-app-1
```

Failure test: stop the database and watch the app become unhealthy.

```bash
docker compose stop db
curl -i http://localhost/health    # 503, database error
docker compose start db
```

### Lab 3: Monitoring
Open http://localhost:8081, then **Docker Containers** and pick a container to see its
CPU, memory and network graphs. A quick text view of the same data:

```bash
docker stats --no-stream
```

### Lab 4: Secrets come from Vault, not the environment

The app container has no password in its environment:

```bash
docker compose exec app env | grep -i -E 'pass|db_'    # only DB_HOST / DB_PORT
grep -i pass .env                                      # nothing
```

Least privilege — the app's own token can read its secret but not the root password:

```bash
docker compose exec app python -c "
import hvac
c = hvac.Client(url='http://vault:8200')
c.auth.approle.login(
    role_id=open('/vault/approle/role_id').read().strip(),
    secret_id=open('/vault/approle/secret_id').read().strip())
print(c.secrets.kv.v2.read_secret_version(path='db/app', mount_point='nullops',
      raise_on_deleted_version=True)['data']['data']['username'])
c.secrets.kv.v2.read_secret_version(path='db/root', mount_point='nullops',
      raise_on_deleted_version=True)      # hvac.exceptions.Forbidden
"
```

Sealing Vault takes the app's credential source offline; the already-running app keeps
its cached credentials, but a fresh container cannot start:

```bash
ROOT_TOKEN=$(docker compose run --rm --entrypoint "" -T vault-bootstrap \
  awk '/^Initial Root Token:/ {print $4}' /vault/init/init.txt)
docker compose exec -e VAULT_TOKEN="$ROOT_TOKEN" vault vault operator seal
docker compose up -d vault-bootstrap       # unseals it again
```

### Lab 5: Rotating the database password

Change it in MariaDB and in Vault; the app picks the new value up on its next query,
without a restart (it re-reads Vault when MariaDB answers "access denied"):

```bash
ROOT_TOKEN=$(docker compose run --rm --entrypoint "" -T vault-bootstrap \
  awk '/^Initial Root Token:/ {print $4}' /vault/init/init.txt)
NEW_PASS=$(docker compose exec -T vault sh -c 'tr -dc A-Za-z0-9 </dev/urandom | head -c 32')

docker compose exec -T db sh -c "mariadb -uroot -p\"\$(cat /run/secrets/db_root_password)\" \
  -e \"ALTER USER '\$(cat /run/secrets/db_user)'@'%' IDENTIFIED BY '$NEW_PASS'\""
docker compose exec -e VAULT_TOKEN="$ROOT_TOKEN" -T vault \
  vault kv patch nullops/db/app password="$NEW_PASS"

curl -s http://localhost/          # still works, now with the new password
```

### Persistence check

```bash
curl http://localhost/                       # note total_visits
docker compose down && docker compose up -d
curl http://localhost/                       # counter continues, data survived
```

Vault's storage volume survives the same way: on the next start `vault-bootstrap` finds
Vault already initialised, unseals it and keeps the stored passwords.

### Scaling the app

```bash
docker compose up -d --scale app=3
for i in 1 2 3 4 5 6; do curl -s http://localhost/; echo; done   # served_by changes
```

Each replica logs into Vault on its own with the same AppRole. Nginx resolves `app` once
at startup, so restart it after scaling: `docker compose restart nginx`.

## Notes

- On Docker Desktop (Windows/macOS) cAdvisor shows fewer host-level metrics than on a
  Linux host, because it runs inside Docker's VM; per-container metrics still work.
- `docker compose down -v` deletes the `vault-data` and `dbdata` volumes together. Do not
  delete only one of them: Vault would hand out a new password that the existing database
  does not know.
